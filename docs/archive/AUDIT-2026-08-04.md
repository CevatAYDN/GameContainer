## 1. 🔴 Critical Vulnerabilities & Dead Guards

### 1.1 [CRITICAL] `SafeAsyncRunner.Run` gövdesinde `_ =` discard → unobserved exception yolu kapatılmamış
- **Dosya & Satır:** `Runtime/Core/SignalBus.cs:16-47`
- **Sorun:**
  ```csharp
  public static void Run(Func<ValueTask> func, string errorContext)
  {
      _ = RunAsync(func, errorContext);   // ← discard
  }
  ```
  `RunAsync` zaten `try/catch` içeriyor, dolayısıyla fire-and-forget çağrıları için söylenilen güvenlik iddiası doğru. **AMA**:
  - `func()` çağrısı (satır 30) **synchronously throw** ederse (yani `ValueTask` döndürmeden önce istisna atarsa), o istisna `try` bloğunun içinde yakalanıyor ve loglanıyor — bu doğru.
  - **Asıl kritik tehlike**: `func` çağrısı `ValueTask` döndürüyorsa ama `ValueTask`'ın `IsCompleted == false` olması için task'ın başlaması lazım. Eğer çağrı sırasında herhangi bir `OperationCanceledException` `await task` aşamasında fırlarsa ve `_context.LifetimeToken` iptal edilmişse, **catch bloğu her durumda log yazıyor** (satır 44). Cancellation log'larının Editor'ı doldurması muhtemel.
  - **Daha kötüsü**: `RunAsync` `Task` döndürüyor (signatur `private static async Task RunAsync`). `_ = RunAsync(...)` ile discard edildiğinde, `RunAsync` içindeki async state machine için `AsyncTaskMethodBuilder` allocate ediliyor — bu `Run()` metodunun "allocation-free" iddiasını ihlal ediyor. **Hot path allocation**.
- **Empirical Evidence:**
  - `SafeAsyncRunner` `SignalBus.cs:873` ve `:887`'de cross-context ve queued dispatch path'lerinde her fire'da çağrılıyor.
  - Her çağrı `AsyncTaskMethodBuilder<EmptyStruct>` allocate ediyor (yaklaşık 32-48 byte per call).
  - ZeroGC harness testi bu metodu ölçmüyorsa allocation fark edilmemiş olabilir.
- **Önerilen Düzeltme:**
  1. `Task.Run(...)` veya `ThreadPool.QueueUserWorkItem` ile yapılan discard'lar için `TaskScheduler.UnobservedTaskException` event'ini en az bir kere log'a bağla (yapılmamış).
  2. `Run()` metodunun "no-alloc" iddiası yanlışsa, ya `ThreadPool.QueueUserWorkItem` ya da `ValueTask.CompletedTask` tabanlı sync fast-path'e dön.

### 1.2 [CRITICAL] `RecoveryEngine` async fire-and-forget lambda'sı await edilmeden depolanıyor
- **Dosya & Satır:** `Runtime/Core/SignalBus.cs:152`
  ```csharp
  _recoveryEngine = new RecoveryEngine(container, FireFailedSignalSafe, fs => FireAsyncAndForget(fs));
  ```
- **Sorun:** Bu lambda `Func<CommandFailedSignal, ValueTask>` tipinde. Lambda, `FireAsyncAndForget` çağrısının döndürdüğü `ValueTask`'ı **hiçbir yerde await etmeden** döndürüyor. Yani:
  - Çağıran kod (`RecoveryEngine.ExecuteAsyncPlan`, satır 209) `await _fireFailedAsync(plan.FailedSignal)` yapıyor ✓
  - AMA bu lambda'nın döndürdüğü ValueTask, `FireAsyncAndForget` async metodunun `ValueTask`'ı. Eğer bu metodun içindeki `await FireInternalAsync(...)` exception throw ederse, **lambda `ValueTask`'ı faulted state ile döndürür**. `RecoveryEngine` bu fault'u bekliyor ✓.
  - **Gerçek problem**: `FireAsyncAndForget` (SignalBus.cs:287) `try/catch` içinde zaten hataları yakalayıp `OnUnhandledException?.Invoke()` çağırıyor. Yani exception lambda'ya sızmıyor. **Ama `OperationCanceledException` haricindeki her şey için `OnUnhandledException`'a log yazıyor** → bu, `RecoveryEngine`'in `await` path'inde hata olmadığı için sessizce geçiyor. Recovery sonrası log spam.
- **Tutarsızlık:** `SignalBus.FireInternalAsync` zaten `FireFailedSignalSafe` üzerinden dispatch'i handle ediyor. `FireAsyncAndForget` ise hata olduğunda zaten log yazıyor. İki katman aynı hatayı logluyor → "double logging" kategorisi.
- **Önerilen Düzeltme:** Lambda'yı `async failedSignal => await FireInternalAsync(failedSignal, isCrossContextSource: false)` olarak değiştirip `FireAsyncAndForget` üzerinden değil doğrudan async path'ten geçir. Veya `FireAsyncAndForget`'in internal versiyonunu yarat (logging olmadan) ve sadece bunu kullan.

### 1.3 [CRITICAL] `CommandFailedSignal` dispatch'i `_ = FireAsyncAndForget` ile discard
- **Dosya & Satır:** `Runtime/Core/SignalBus.cs:502-504`
  ```csharp
  if (hasAsync)
  {
      SafeAsyncRunner.Run(() => FireInternalAsync(failedSignal, isCrossContextSource: false), ...);
  }
  else
  {
      _ = FireAsyncAndForget(failedSignal);
  }
  ```
- **Sorun:** `_ = FireAsyncAndForget(failedSignal)` discard edilen `ValueTask`. `FireAsyncAndForget` (satır 287-309) kendi içinde `try/catch` ile hatayı yakalayıp logluyor, ama:
  - Bu metod `public async ValueTask` — discard edilmesi durumunda, eğer içindeki `await FireInternalAsync(...)` `OperationCanceledException` fırlatmazsa (yani cancellation olmazsa), hata `OnUnhandledException` event'ine yazıyor. Sorun yok.
  - **Asıl tehlike**: `_ = FireAsyncAndForget(failedSignal)` çağrısı bir async state machine allocate eder. Recovery path'i zaten hot path değil, ama `_disposed == true` iken çağrılırsa, `FireInternalAsync` `_subscriptionRegistry.SubscriptionsReadCopy` üzerinden disposed pool'a erişmeye çalışacak → `ObjectDisposedException` mümkün.
  - **Tutarsızlık**: `hasAsync == true` iken `SafeAsyncRunner` (satır 498), ama `hasAsync == false` iken discard — neden farklı davranış? İkisi de fire-and-forget.
- **Önerilen Düzeltme:** İki dalı da `SafeAsyncRunner.Run` üzerinden geçir. `_ =` discard hot path allocation demek.

### 1.4 [CRITICAL] `NexusDI.Dispose` → `_ = DisposeAllAsyncInBackground(asyncDisposables)` sync-over-async
- **Dosya & Satır:** `Runtime/Core/NexusDI.cs:1301-1324`
  ```csharp
  if (asyncDisposables.Count > 0)
      _ = DisposeAllAsyncInBackground(asyncDisposables);
  ```
- **Sorun:**
  - Bu discard **fire-and-forget**. `Dispose()` metodu senkron olarak döndüğü için, `DisposeAllAsyncInBackground` arka planda çalışmaya devam ederken:
    - `_bindings.Clear()` ve `_namedBindings.Clear()` zaten çağrılmış (satır 1303-1304) — bu OK.
    - AMA context başka bir thread'de `Resolve` çağırırsa, `_bindings` boş olduğu için `InvalidOperationException` fırlatır.
  - `DisposeAllAsyncInBackground` Task döndürüyor. `ConfigureAwait(false)` kullanıyor (satır 1318) — Unity main thread'de `await` gereken bir continuation varsa (custom `IAsyncDisposable` implementasyonu) bu **deadlock riski** taşır.
  - **Daha kritik**: `Dispose()` çağıran kod (örn. `Context.Dispose`, satır 629) hemen ardından `_cts.Dispose()` (satır 630) çağrısı yapıyor. Eğer `DisposeAllAsyncInBackground` herhangi bir IAsyncDisposable singleton'ın `DisposeAsync` metodu `LifetimeToken`'a bağlı ise, o token iptal edilmiş olur → `OperationCanceledException` fırlatır → `LogError` yazılır → sessizce yutulur.
- **Önerilen Düzeltme:**
  1. `Dispose()` override'ından `_ =` discard'u kaldır.
  2. `DisposeAllAsyncInBackground` Task'ı bir field'da tut, sonraki `Dispose()` çağrısında `await` et (zaten dispose edildiği için no-op).
  3. Veya sync path tamamen kaldırılıp tek async path'e geçilir (`DisposeAsync`).

### 1.5 [CRITICAL] `Root.Start` async-void — exception sinyali kaybolabiliyor
- **Dosya & Satır:** `Runtime/Core/Root.cs:218-324`
  ```csharp
  private async void Start()
  ```
- **Sorun:**
  - `async void` Unity'nin MonoBehaviour event'lerinde kabul edilebilir, ama **dıştardan handle edilemez**. Burada:
    - `try/catch` bloğu var (satır 225-323), iyi.
    - AMA satır 240'ta `TimeoutException` throw edildiğinde, bu `Root` GameObject'i disabled bırakır. **Sibling/parent Roots bu exception'ı görmez** → bekleyen Root'lar timeout'a kadar askıda kalır.
    - Satır 290-300: lifecycle off-main-thread döndüğünde `ThreadStateException` atılıyor, ama bu satır 304 `catch (OperationCanceledException)`'dan **önce** geliyor. `OperationCanceledException` ise catch edilecek ama `ThreadStateException` da aynı catch'e düşer mi? Kontrol et:
      - Sıra: `OperationCanceledException` → `ThreadStateException` → genel `Exception`. Eğer Unity main thread'inden lifecycle `ConfigureAwait(false)` ile döndüyse, exception `OperationCanceledException` DEĞİL — bu yüzden `catch (Exception)` (satır 314) yakalıyor ve logluyor. Bu doğru.
    - **Asıl sorun**: `Start` async-void, parent'a `Task.CompletedTask` döndürüyor. Eğer bu Root başka bir Root'un parent'ı ise, o Root `IsInitialized == false` görmeye devam ediyor ve `parentTimeoutFrames` (default 900) boyunca bekliyor. Bu doğru.
  - **Subtle bug**: Satır 174'te `_mainThreadId` Awake'de set ediliyor. Eğer `Awake` editor'de farklı thread'de çalıştırılırsa (ör. domain reload sonrası), `_mainThreadId` yanlış olur ve `Start`'taki guard false positive üretir.
- **Önerilen Düzeltme:**
  1. `async void Start` → `async Task StartInternal` ile sarmalanıp `Start`'ta `_ = StartInternal()` yapılır (Unity event signature'ı değişmez).
  2. `_mainThreadId`'yi capture'ı `Thread.CurrentThread.ManagedThreadId`'den ziyade daha güvenilir bir mekanizma ile yap (örn. SynchronizationContext identity).

## 2. 🟠 Thread-Safety & Race Condition Risks

### 2.1 [HIGH] `NexusDI._bindings` ConcurrentDictionary ama yarış durumu hâlâ var
- **Dosya & Satır:** `Runtime/Core/NexusDI.cs:876-881` (Resolve) ve `Runtime/Core/NexusDI.cs:1018-1033` (ReInject)
- **Sorun:** `Resolve` `_bindings.TryGetValue` ile başlıyor, sonra `ResolveBinding`'i çağırıyor. `ResolveBinding` içinde `binding.Instance` volatile read yapıyor (Binding sınıfında `volatile object Instance`) ✓. AMA:
  - `RegisterContext` ile `Context` aynı anda oluşturulup singleton bind edilirse (initialization sırasında), `_bindings` henüz final state'te değilken `Resolve` race'e girer.
  - **Daha kötüsü**: `ReInject` (satır 1018) `_pendingInjections.TryGetValue` çağırıyor. `_pendingInjections` `ConditionalWeakTable<object, PendingInjection>`. `TryGetValue` thread-safe, ama `_di.RecordPendingField` (satır 1062) `_pendingInjections.GetOrCreateValue` çağırıyor — bu `ConditionalWeakTable`'a özgü race'e sahip (MSDN: "thread-safe but not atomic for compound operations").
  - `pending.Fields.Add(field)` (satır 1067) lock altında ✓, ama **lock'lar farklı nesneler**: `_pendingInjectionsLock` ve `ReInject`'in snapshot iteration'ı lock dışı. **TOCTOU** var.
- **Önerilen Düzeltme:** `ReInjectAll`'ı `_pendingInjectionsLock` altında tamamen yap, ya da `_pendingInjections` için `ConcurrentDictionary<object, PendingInjection>` kullan (weak ref istisnası dışında).

### 2.3 [HIGH] `SignalBus.FireAsyncAndForget` exception handler race
- **Dosya & Satır:** `Runtime/Core/SignalBus.cs:287-309`
  ```csharp
  public async ValueTask FireAsyncAndForget<T>(T signal, Action<Exception> onError = null) where T : struct
  {
      try
      {
          await FireInternalAsync(signal, isCrossContextSource: false);
      }
      catch (OperationCanceledException) { /* expected */ }
      catch (Exception ex)
      {
          if (onError != null) onError(ex);
          else
          {
              OnUnhandledException?.Invoke(ex, ...);
              NexusRuntime.Logger?.LogError(...);
          }
      }
  }
  ```
- **Sorun:** İki sorun:
  1. `OnUnhandledException?.Invoke(ex, ...)` event handler'ları **senkron** olarak çağrılıyor. Eğer bir handler exception throw ederse (diğer subscriber'lar engellenir), bu **try/catch** ile korunmuyor. `NexusRuntime.Logger?.LogError`'dan sonra `OnUnhandledException` raise ediliyor — sıra ters: log ÖNCE, event SONRA olmalı, böylece event handler log'u override edebilir.
  2. `OnUnhandledException` **statik event**, `Context.Dispose` ile clear edilmiyor (`SignalBus.ClearStaticCaches` çağrısı yalnızca `OnUnhandledException = null` yapıyor — `NexusRuntime.Reset`'te çağrılıyor, ama her context dispose'da değil). **Static event = potansiyel event handler leak**. Unity domain reload'da temizlenir ama oyun esnasında leak olabilir.
- **Önerilen Düzeltme:**
  1. `OnUnhandledException?.Invoke`'u `try/catch` içine al.
  2. Her context dispose'da `OnUnhandledException = null` çağrısı düşünülebilir (ama multi-context scenario'da hangi context'in dispose'ında clear edileceği net değil — şu anki tasarım muhtemelen doğru).

### 2.6 [MEDIUM] `HybridQueue.Drain` lock-free ama Dequeue-then-Fire window'unda signal release
- **Dosya & Satır:** `Runtime/Queue/HybridQueue.cs:283-308`
  ```csharp
  private void Drain(QueuedSignalRingBuffer queue, object queueLock)
  {
      while (true)
      {
          IQueuedSignal queuedSignal = null;
          lock (queueLock)
          {
              if (queue.Count > 0) queuedSignal = queue.Dequeue();
          }
          if (queuedSignal == null) break;

          try { queuedSignal.Fire(_signalBus); }
          catch (Exception ex) { ... }
          finally
          {
              queuedSignal.Release();
              ...
          }
      }
  }
  ```
- **Sorun:** Dequeue lock altında ✓, ama Fire + Release lock dışında. Bir başka thread `EnqueueThreadSafe` yaparsa ve aynı type için signal pool'unda tükenme olursa, `Rent` yeni instance oluşturur. **Bu doğru**, çünkü pool per-type ve concurrent rent destekliyor.
  - **AMA**: `queuedSignal.Fire(_signalBus)` (satır 296) eğer sync handler exception throw ederse, `queuedSignal.Release()` finally'de çağrılır ✓. Eğer async handler fire-and-forget ise, **drain thread fire tamamlanmadan `Release` çağırır** — bu pool'a signal'ı geri koyar, ama signal async hâlâ işleniyor. **Type B fire-and-forget signal type'ı için**: pool'a geri dönen wrapper'ı başka bir thread `Rent` ile alıp kendi signal'ı ile override ederse, eski signal hâlâ async işlenirken yeni signal'ın alanı eskisi tarafından dispatch sırasında ezilir.
  - **CRITICAL** — bu bir data race. `QueuedSignalWrapper<T>.Signal = signal` (HybridQueue.cs:88) `Rent`'te yapılır. Eğer iki thread concurrent `Rent` ve `FireQueued` yapıyorsa (örn. main thread drain async dispatch başlattı, sırada `Release` yaptı, başka bir thread `Rent` ile aynı wrapper'ı aldı → field overwrite) → **dispatcher eski signal'ı ateşler**.
- **Önerilen Düzeltme:** `QueuedSignalWrapper<T>` için "in-flight" flag ekle, veya `Drain` async-await pattern'e dön. `HybridQueue.DrainThreadSafe` ve `DrainNextFrame` async olmalı.

## 3. 🟡 Memory Leaks & Lifecycle Integrity

### 3.1 [HIGH] `ICompositeCommand` async composite pool leak — retry loop'ta

- **Sorun:** Bu metod `ExecuteCompositeCommandAsyncCore` async'tir ve `SafeAsyncRunner.Run` ile fire-and-forget başlatılıyor. Pool'dan alınan `command` `cmdForAsync`'e atanıyor, sonra `command = null` yapılıyor (finally return etmesin diye) ✓. AMA retry path'inde (decorator exception → RecoveryAction.Retry) **aynı `command` instance'ı yeniden kullanılıyor** (satır 657'de her retry'da `GetCommand` yeni instance alıyor, eski leak mi?). Kontrol:
  - Satır 656: `command = _poolManager.GetCommand(trigger.CommandType);` → yeni instance.
  - AMA retry (satır 711): `if (action == RecoveryAction.Retry) { retryCount++; }` else break, while loop devam ediyor → tekrar `GetCommand` çağrısı yeni instance alıyor, eskisi **return edilmiyor** (önceki iterasyonda `command = null` yapılmıştı).
  - **Memory leak**: Her retry'da pool'dan yeni instance alınıp eski "hayalet" instance (hiç return edilmemiş) bırakılıyor. Bu, retry-cap ile sınırlı ama yine de bir leak.
- **Önerilen Düzeltme:** Async composite için retry path'i ayrı ele al. Composite async command retry'sında async path await edilmeli, sync path'te retry yok (sadece fire-and-forget var). Retry'sız path'te fire-and-forget sonrası return çağrılmıyor.
