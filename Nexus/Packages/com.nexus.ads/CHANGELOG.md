# Changelog

## Unreadable reward row quarantine (#415)

- An unreadable `nexus.ads.reward.pending` row (bad base64, wrong field count, duplicate id,
  unknown header) no longer blocks every later payout. The next earned reward copies the raw row
  to `nexus.ads.reward.pending.corrupt.<n>` (first free `n`, never overwriting an earlier one),
  then writes its receipt to a queue that restarts empty, so `DeliveringReward` is set.
  The copy is written first: a failing store leaves the row untouched and the write fails.
  A conflicting reward id, or a store `IOException`, never quarantines.
- New `AdEventKind.RewardQuarantined` (appended last; the detail names the key), written in
  every build by `AdFailureLog`.
- New explicit recovery for startup replay: `RewardReceipts.QuarantineUnreadable(store)`,
  `AdController.QuarantineUnreadableRewards()` and `Ads.QuarantineUnreadableRewards()` move an
  unreadable row aside and empty the queue, returning the key, or return null and write nothing
  when the row is readable. `PendingReward` and `AcknowledgeReward` still throw on an unreadable
  row and never write. The rewards that row held are not recovered.

## Caller offer context (#414)

- Contextual `Show` / bridge `RequestReward` overloads capture an opaque caller
  token before provider work. `RewardReceipt.Context` persists it on live, late and
  replayed rewards. Existing calls/constructors use null context.
- NXRQ3 reads NXRQ2 and legacy single receipts without inventing tokens. All
  mutations retain each receipt's own context; unknown/corrupt formats fail closed.
- Non-null context on unsupported custom services/adapters throws before showing.
  The context-aware async grant overload preserves grant-before-ack semantics.
- Games must retain immutable offer records and use Context for offer lookup,
  Id for payment deduplication. No automatic repair of old ambiguous offers.

## Reward queue correction (#413)

- Late reward A is no longer overwritten by B. All unacknowledged receipts live in one
  versioned row; `PendingReward` returns the oldest and acknowledgement removes only its id.
  Legacy `id|placement` is read and migrated on mutation. Corrupt queue data is preserved with
  an exception. Do not downgrade with pending queued data.
- Added `Ads.DeliveringReward` for facade users; live callbacks must use their delivery id,
  while startup replay drains `PendingReward` until empty and stops on failures. Consumers
  must retain idempotency for out-of-order ids (`EarnOnce` or an atomic applied-id ledger).
- `RewardReplaced` remains for enum compatibility; built-in receipt writes no longer emit it.
  The historical #178 single-slot behavior documented below is superseded.

## [Unreleased]

### Fixed
- **Build-owned reward fault inclusion** (#420). The ads family uses `NEXUS_ADS_FAULT_TESTS`, set from the actual player build's Development option and removed for release; runtime code no longer uses the deprecated `DEVELOPMENT_BUILD` symbol or suppresses UAC0009. The package build hook covers the bootstrap, debug panel, LevelPlay and AdMob together. Script-only compilation tools must supply the family define explicitly.
- **Recurring controller timers reuse their cancellation state** (#418 follow-up). `IAdScheduler.CreateTimer` supplies an owner-held `IAdTimer` with Reset/Cancel/Dispose; Unity resets without allocation after list warmup, while custom schedulers keep a compatible default implementation. Controller pacing, load retries, initialization and answer/show deadlines create their timers/callbacks once; LevelPlay and UMP network polling reuse timers too. The existing one-shot Schedule contract keeps distinct tokens so stale handles remain harmless.
- **Scheduled-wait coroutine allocations** (#418): `UnityAdScheduler` uses an unscaled deadline list instead of creating an iterator, yield object and Coroutine per wait. Waiting/dispatch bookkeeping allocates nothing after list capacity is warmed; `Schedule` retains one unique cancellation-token allocation so a stale `IDisposable` cannot cancel a later wait. Reentrant zero-delay work waits until a later frame; cancellation, disabled-host cleanup and time-scale-zero behavior are covered.
- **Idle development JNI allocations** (#416): reward fault Intent commands read at startup and focus gain instead of polling twice a second. Foreground adb users send HOME before `am start`; held rewards stay in the same process. Release assemblies still exclude the entire fault API.

Found and verified on a phone (2311DRK48G, Android 16): Google's test ads shown, rewarded paid once, interstitial closed; LevelPlay's SDK started and reached its server.
